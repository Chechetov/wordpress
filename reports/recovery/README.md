# Восстановление упавшей части сетки

Состояние на 29.08.2026. Из 49 доноров **20 лежат**, 29 живы. Обход выполнен браузером
(Cloudflare-челлендж не даёт проверить сетку ни curl-ом, ни через WP REST).
Полный статус по каждому домену — `../network_health_20260829.csv`.

## Почему бэкапы не спасут

Проверено и подтверждено:

- Локально бэкапов нет — ни дампов БД, ни архивов `wp-content` (искал по всему `~`).
- В Timeweb Cloud на сервере `Inventive Crossbill` (8753337) — **нет ни бэкапов, ни
  снапшотов, ни образов**, автобэкапы не настроены.
- В веб-архиве наших статей нет: из 25 проверенных URL кампаний найдено **0**.
  Wayback помнит только прошлые жизни этих доменов (снимки до 2024–2025 гг.).

Единственный уцелевший источник — контент-планы, и они покрывают потерю **полностью**.

## Из чего восстанавливаем

241 статья (121 с анкором) по всем 20 упавшим донорам, разложенная по кампаниям.
Каждый пакет — пара «сайты + план» в формате, который `publish_all.py` принимает
как есть; ID сайтов перенумерованы с 1, рубрики и анкоры сохранены.

| Пакет | Доноров | Статей | Файлы |
|-------|---------|--------|-------|
| c1 | 3 | 18 | `c1_sites.json`, `c1_plan.csv` |
| c2 | 17 | 102 | `c2_sites.json`, `c2_plan.csv` |
| c3 | 13 | 78 | `c3_sites.json`, `c3_plan.csv` |
| c4 | 7 | 43 | `c4_sites.json`, `c4_plan.csv` |

Все четыре пакета прогнаны через `--dry-run` — расписание строится, статьи на месте.

## Порядок восстановления

**1. Поднять хостинг.** Две группы поломок, чинятся по-разному:

- *Cloudflare 521* (10 доменов: drunk-fish, kgdink, mai-hoshi, omegabay, prforce,
  property-in-alanya, speciallabel, techfile, top-audit, unit-org) — origin выключен.
  Все десять из кампаний 2+3, то есть это один хостинг целиком.
- *Бесконечный редирект* (10 доменов: 2semechki, avtogear62, promplo, kakudobrit,
  ledpnz, elintel, pro-covers, yellodigital, доступныйсервис.рф, стандарт72.рф) —
  origin отвечает, но гоняет по кругу. Сначала проверить SSL-режим в Cloudflare:
  при **Flexible** CF идёт на origin по HTTP, а тот форсирует HTTPS — вот и петля.
  Переключение на **Full** может поднять эти сайты без всякого передеплоя.

**2. Проверить, живы ли файлы и БД.** Если WordPress уцелел — публиковать заново
ничего не нужно, статьи вернутся сами. Передеплой нужен только там, где данные потеряны.

**3. Снять Cloudflare-челлендж с API.** Пока на зонах висит челлендж, `publish_all.py`
не достучится до `/wp-json/` ни напрямую, ни через прокси (старый прокси
`80.78.26.205:32223` мёртв). Чистое решение — WAF-правило Skip для пути `/wp-json/*`
с рабочего IP, либо выключить Bot Fight Mode на время прогона. Это убирает
зависимость от прокси вообще.

**4. Опубликовать.** Для каждого пакета:

```bash
python3 publish_all.py --sites-file reports/recovery/c2_sites.json \
                       --plan       reports/recovery/c2_plan.csv \
                       --dry-run                      # сначала посмотреть расписание
python3 publish_all.py --sites-file reports/recovery/c2_sites.json \
                       --plan       reports/recovery/c2_plan.csv \
                       --workers 5 --image-backend openai --image-quality low
```

Даты в планах прошедшие, поэтому статьи встанут задним числом — так и задумано,
это восстанавливает исходную хронологию сетки.

**5. Сверить факт.** После прогона:

```bash
python3 reconcile_campaign.py   # сверяет план с фактическим состоянием сайтов
python3 verify_campaign.py      # проверяет анкоры, траст-ссылки, обложки, nofollow
python3 check_network.py --proxy # общая живость всех 49 доноров
```

## Что помнить про URL

Слаги WordPress генерирует из заголовка, а модель переписывает заголовки вольно, —
значит **URL восстановленных статей не совпадут с прежними**. Прежние адреса лежат
в `../network_published_urls.csv` (237 размещений). Если важно вернуть именно старые
URL ради ссылочного веса, слаги нужно проставлять принудительно из этого файла;
сейчас такой опции в `publish_all.py` нет.
