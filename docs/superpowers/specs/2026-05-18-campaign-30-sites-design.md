# Кампания: 30 сайтов × 6 статей

**Дата:** 2026-05-18
**Статус:** утверждён дизайн, ожидается реализация

## Цель

Опубликовать на 30 новых сайтах по 6 статей (всего 180) с отложенным
расписанием. На каждом сайте размещается одна статья с клиентским анкором
(ссылка на `aso-cdo.ru`), две статьи с трастовыми анкорами и три тематические
статьи без ссылок. Расписание для каждого сайта начинается от даты последней
уже опубликованной на нём статьи и продолжается с интервалом 1–2 дня.

## Структура контента

### На каждый сайт — 6 статей

| Тип | Кол-во | Анкор | Ссылка |
|---|---|---|---|
| `анкор клиента` | 1 | клиентский анкор из таблицы | целевая страница `aso-cdo.ru` |
| `траст` | 2 | сгенерированный анкор-слово | авторитетный ресурс (Wikipedia, gov.ru, hh.ru, Росстат и т.п.) |
| `` (пусто) | 3 | — | — |

### Порядок статей в очереди сайта

Шесть статей публикуются последовательно. Клиентская анкорная статья ставится
на позицию 2, 3 или 4 (выбор случайный) — не первой, чтобы выглядеть
естественно среди прочего контента. Две трастовые и три тематические
распределяются по оставшимся позициям случайно.

### Привязка анкоров к сайтам

30 анкоров → 30 сайтов, 1:1, по порядку списка сайтов. Сайты не привязаны к
конкретным городам. Рубрика сайта и темы 6 статей локализуются под город
анкора (Красноярск / Москва / Тюмень) и под тематику целевой страницы.

## Контент-план

Генерируется `content_plan.csv` (180 строк) в текущем формате:

```
Сайт;Рубрика;Тема статьи;Анкор;Ссылка;Тип
```

- `Сайт` — id сайта (1–30).
- `Рубрика` — одна на сайт, тематически связанная с городом и анкором.
- `Тема статьи` — генерируется под город и тему; трастовые ссылки подбираются
  контекстно к теме статьи.
- Порядок строк внутри блока сайта = порядок публикации.

**Гейт согласования:** готовый `content_plan.csv` показывается заказчику до
запуска публикации.

## Расписание

Дорабатывается `publish_all.py` — добавляется чтение даты последней статьи.

### Логика

1. Для каждого сайта через WP REST API запрашивается последняя статья:
   `GET /wp-json/wp/v2/posts?orderby=date&order=desc&per_page=1` со статусами
   `publish` и `future`.
2. Первая новая статья сайта планируется через 28–52 ч (1–2 дня) после даты
   последней существующей статьи.
3. Каждая следующая — через 28–52 ч после предыдущей.
4. Часы публикации 8:00–21:00, минуты случайные (не ровные часы).
5. Если расчётная дата оказывается в прошлом (последняя статья сайта старая)
   **или** статей на сайте нет — отсчёт начинается от `сейчас + 1–6 ч`.
6. Статьи создаются со статусом `future`; публикует их сам WordPress.

### Изменения в коде

- Новая функция `get_last_article_date(site_config)` — возвращает `datetime`
  последней статьи или `None`.
- Функция `build_schedule` заменяется на `build_site_schedule(last_date,
  num_articles)` — строит расписание одного сайта от переданной даты.
- Расписание строится после определения прокси и даты последней статьи,
  внутри обработки каждого сайта.

*Отклонённая альтернатива:* отдельный скрипт `publish_campaign.py`. Логика
почти полностью дублирует `publish_all.py`, который ещё не закоммичен, —
поэтому дорабатываем существующий файл.

## Запуск

1. Заказчик присылает Application Passwords → формируется `sites.json` на 30
   сайтов.
2. `python publish_all.py --dry-run` — выводится полное расписание всех 180
   статей по датам. Заказчик подтверждает.
3. Реальный запуск: генерация текста (OpenAI), обложек (Imagen), публикация со
   статусом `future`. 180 статей — прогон длительный, запускается в фоне.
4. Отчёт сохраняется в `reports/publish_all_<timestamp>.json`.

## Критерии готовности

- `content_plan.csv` содержит 180 строк (30 сайтов × 6), согласован заказчиком.
- `publish_all.py` строит расписание от даты последней статьи каждого сайта.
- `--dry-run` показывает корректное расписание без публикации.
- После реального запуска: 180 статей со статусом `future`, в каждом блоке
  сайта 1 анкорная + 2 трастовых + 3 тематических, анкорная не первая.
- Отчёт без ошибок (или ошибки разобраны).
