# Кампания: 29 сайтов × 6 статей

**Дата:** 2026-05-18
**Статус:** утверждён дизайн, ожидается реализация

## Цель

Опубликовать на 29 новых сайтах по 6 статей (всего 174). На каждом сайте
размещается одна статья с клиентским анкором (ссылка на `aso-cdo.ru`), две
статьи с трастовыми анкорами и три тематические статьи без ссылок.
Расписание продолжает таймлайн прошлой кампании: отсчёт ведётся от даты
последнего анкора предыдущего захода (22 апреля 2026), сайты стартуют со
сдвигом 1–2 дня, статьи с прошедшими датами публикуются задним числом, с
будущими — через отложенную публикацию WordPress.

### 29 сайтов

Заказчик прислал список из 49 сайтов: 20 — из прошлой кампании (исключены),
29 — новые. Кампания идёт только на 29 новых. Формируется отдельный конфиг
`campaign2_sites.json` в текущем формате (`id`, `domain`, `url`, `username`,
`password`); существующий `sites.json` (20 старых сайтов) не трогаем.

## Структура контента

### На каждый сайт — 6 статей

| Тип | Кол-во | Анкор | Ссылка |
|---|---|---|---|
| `анкор клиента` | 1 | клиентский анкор из таблицы | целевая страница `aso-cdo.ru` |

| `` (пусто) | 3 | — | — |

### Порядок статей в очереди сайта

Шесть статей публикуются последовательно. Клиентская анкорная статья ставится
на позицию 2, 3 или 4 (выбор случайный) — не первой, чтобы выглядеть
естественно среди прочего контента. Две трастовые и три тематические
распределяются по оставшимся позициям случайно.

### Привязка анкоров к сайтам

29 анкоров → 29 сайтов, 1:1, по порядку списка сайтов. Сайты не привязаны к
конкретным городам. Рубрика сайта и темы 6 статей локализуются под город
анкора (Красноярск / Москва / Тюмень) и под тематику целевой страницы.

## Контент-план

Генерируется новый `content_plan.csv` (174 строки) в текущем формате:

```
Сайт;Рубрика;Тема статьи;Анкор;Ссылка;Тип
```

- `Сайт` — id сайта (1–29).
- `Рубрика` — одна на сайт, тематически связанная с городом и анкором.
- `Тема статьи` — генерируется под город и тему; трастовые ссылки подбираются
  контекстно к теме статьи.
- Порядок строк внутри блока сайта = порядок публикации.

**Гейт согласования:** готовый `content_plan.csv` показывается заказчику до
запуска публикации.

## Расписание

Расписание продолжает таймлайн прошлой кампании. Дорабатывается `publish_all.py`.

### Опорная точка

Последний анкор прошлой кампании — **2026-04-22 16:53** (см.
`reports/anchors_audit.md`). От него ведётся отсчёт. Даты новых статей **не**
читаются с новых сайтов через API — это уточнено заказчиком.

### Логика

1. Сайты публикуются со сдвигом: старт серии каждого следующего сайта — через
   28–52 ч (1–2 дня) после старта предыдущего. Старт первого сайта — опорная
   точка + 28–52 ч.
2. Внутри сайта 6 статей идут последовательно с интервалом 28–52 ч.
3. Часы публикации 8:00–21:00, минуты случайные (не ровные часы).
4. За счёт сдвига стартов анкорные статьи 29 сайтов выходят примерно каждые
   1–2 дня. Ориентировочное окно кампании: ~23 апреля – середина июня
   (точные даты — в выводе `--dry-run`).
5. **Бэкдейтинг.** Для каждой статьи выбирается статус по расчётной дате:
   - дата ≤ «сейчас» → статус `publish`, поле `date` = расчётная прошедшая
     дата (статья публикуется задним числом);
   - дата > «сейчас» → статус `future` (публикует сам WordPress).

### Изменения в коде

- Функция `build_schedule` переписывается: строит расписание всех сайтов от
  опорной даты со сдвигом стартов, без обращения к API.
- В `publish_to_site` добавляется выбор статуса (`publish` / `future`) по
  расчётной дате каждой статьи.
- В `publish_all.py` добавляется аргумент `--sites-file` (по умолчанию
  `sites.json`), чтобы запустить кампанию на `campaign2_sites.json`.
- Чтение даты последней статьи с сайтов (`get_last_article_date`) **не нужно**.

*Отклонённая альтернатива:* отдельный скрипт `publish_campaign.py`. Логика
почти полностью дублирует `publish_all.py`, который ещё не закоммичен, —
поэтому дорабатываем существующий файл.

### Замечание (риск)

Около половины статей создаётся задним числом (апрель – середина мая). На
новых сайтах это может выглядеть так, будто контент существовал раньше
регистрации/индексации сайта. Принято по решению заказчика.

## Запуск

1. Из присланного списка формируется `campaign2_sites.json` (29 новых сайтов).
2. Генерируется `content_plan.csv` (174 строки).
3. `python publish_all.py --sites-file campaign2_sites.json --dry-run` —
   полное расписание 174 статей по датам с пометкой «задним числом /
   отложенная». Заказчик подтверждает.
4. Реальный запуск: генерация текста (OpenAI), обложек (Imagen), публикация.
   Прошедшие даты — статус `publish`, будущие — `future`. 174 статьи — прогон
   длительный, запускается в фоне.
5. Отчёт сохраняется в `reports/publish_all_<timestamp>.json`.

## Критерии готовности

- `content_plan.csv` содержит 174 строки (29 сайтов × 6), согласован заказчиком.
- `publish_all.py` строит расписание от опорной даты (22.04.2026) со сдвигом
  стартов сайтов, без обращения к API.
- `--dry-run` показывает корректное расписание без публикации, с пометкой
  бэкдейт/отложенная для каждой статьи.
- После реального запуска: 174 статьи — прошедшие даты со статусом `publish`,
  будущие со статусом `future`; в каждом блоке сайта 1 анкорная + 2 трастовых
  + 3 тематических, анкорная не первая.
- Отчёт без ошибок (или ошибки разобраны).
